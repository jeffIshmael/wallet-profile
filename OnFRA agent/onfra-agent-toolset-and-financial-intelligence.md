I think you're getting closer to the right direction. The important thing is that OnFRA should not simply expose blockchain data that another agent can fetch independently. It should turn blockchain data into useful financial intelligence that another agent can immediately act on.

For example, another agent can retrieve 500 transactions from a wallet. But it may not know how to classify them, calculate spending, identify dominant tokens, recognize recurring activity, or explain what the transactions mean.

That is where OnFRA becomes valuable.

I'd structure the tools around three things:

1. Wallet intelligence: What does this wallet look like?
2. Financial analysis: What happened to the money?
3. Transaction intelligence: What does a particular transaction mean?

Here is how I'd define them.

# 1. The tools you've proposed

## 1. Analyze Wallet

Core OnFRA tool

This should be one of OnFRA's most important tools. I wouldn't make it simply return a wallet's transactions or balances. It should return a structured financial overview of a wallet, generated by OnFRA's analysis engine.

Think of it as asking OnFRA:

"Give me a financial intelligence profile of this wallet."

Input

| Parameter        | Required | Description                                  |
| ---------------- | -------- | -------------------------------------------- |
| `wallet_address` | Yes      | Wallet to analyze                            |
| `chain`          | Yes      | Blockchain, e.g. Celo                        |
| `period`         | No       | Analysis period, e.g. 30d, 90d, 1y, all-time |

Expected output

```
{
  "wallet_address": "0x...",
  "chain": "celo",
  "analysis_period": "90d",
  "wallet_overview": {
    "wallet_age_days": 420,
    "total_transactions": 850,
    "active_days": 67,
    "unique_counterparties": 34
  },
  "financial_summary": {
    "total_received_usd": 5200.50,
    "total_sent_usd": 3850.25,
    "net_flow_usd": 1350.25
  },
  "token_overview": {
    "dominant_token": "USDC",
    "dominant_token_share": 72.5,
    "unique_tokens": 5
  },
  "activity": {
    "activity_level": "high",
    "most_active_period": "weekdays"
  },
  "insights": [
    "USDC accounts for most of the wallet's transaction volume.",
    "The wallet received more value than it sent during this period.",
    "Activity is concentrated around a small number of counterparties."
  ],
  "data_quality": {
    "complete": true,
    "limitations": []
  }
}
```

The values above are illustrative.

The response should be structured data, not just a paragraph generated by an LLM.

Why? Because another agent could use this response to:

- Decide whether a wallet is primarily used for payments or holding assets.
- Understand the wallet's financial activity before initiating another workflow.
- Compare two wallets.
- Generate a financial summary for a user.
- Decide whether further investigation is necessary.

My recommendation: Make `analyze_wallet` your flagship tool. It should provide the high-level picture, while the other tools provide deeper analysis.

One important distinction: don't pretend that an activity level or wallet classification is a fact directly recorded on the blockchain. Those are OnFRA-derived assessments.

Expected output

```
{
  "statement_id": "stmt_12345",
  "wallet_address": "0x...",
```

```
{
  "wallet_address": "0x...",
  "comparison": {
    "current_period": "2026-10",
    "previous_period": "2026-09"

    },

      "current": 700,
      "previous": 300,

      "current": 57,
```

This is one of the tools I would strongly recommend keeping.

An agent can retrieve a transaction from a blockchain, but it may not easily understand what happened.

OnFRA should take the transaction data and explain it in human language.

Input

| ------------------ | -------- | --------------------------------------- |
| `transaction_hash` | Yes      | Transaction hash                        |
| `chain`            | Yes      | Blockchain                              |
| `wallet_address`   | No       | Wallet whose perspective should be used |

Expected output

```

  "chain": "celo",
  "status": "success",
  "transaction_type": "token_transfer",
  "summary": "The wallet sent 150 USDC to another address.",
```

# 4. One important design decision: What makes OnFRA different?

I want to highlight something because it affects how you build your MCP server, skills, and API.

There are three different levels of blockchain tools:

| Level                     | Example                                             | Who should provide it?         |
| ------------------------- | --------------------------------------------------- | ------------------------------ |
| Raw blockchain data       | Get transaction by hash                             | Blockchain RPC / data provider |
| Processed blockchain data | Get wallet transactions                             | Indexer / data provider        |
| Financial intelligence    | Analyze wallet, compare cash flow, explain activity | OnFRA                          |

I wouldn't spend your differentiation effort rebuilding a basic blockchain explorer.

An external agent should be able to ask OnFRA:

- "What is this wallet's financial activity?"
- "How much did it receive and spend this month?"
- "What are its dominant tokens?"
- "What is its largest spending category?"
- "How does this month compare with last month?"
- "What happened in this transaction?"
- "Generate a statement for this wallet."

And receive structured, consistent, machine-readable answers.

That's a much stronger proposition than simply providing another way to query blockchain transactions.

# 5. How I'd make the tools useful to other agents

There are four implementation rules I'd establish from the beginning:

1. Consistent inputs: Use the same `wallet_address`, `chain`, `period`, and currency conventions across tools wherever applicable.
2. Structured outputs: Return predictable JSON, not just AI-generated paragraphs.
3. Data provenance: Include the period covered, data source, last updated time, and any missing data or limitations.
4. Clear distinctions: Separate facts obtained from the blockchain from OnFRA's calculations, classifications, and interpretations.

For example, every analysis response should make it possible to distinguish:

- `raw_data`: observed blockchain activity.
- `calculated_metrics`: totals, averages, percentages.
- `classifications`: spending categories and transaction types.
- `insights`: OnFRA's interpretation.

This is especially important when another AI agent uses OnFRA's output to make a decision.

## My final recommendation

I'd define OnFRA as:

An onchain financial intelligence layer that turns wallet activity into structured, actionable insights for AI agents and applications.

Your flagship is `analyze_wallet`. Your supporting tools are cash flow, token breakdown, spending breakdown, period comparison, transaction explanation, balances, and statement generation.

One last thought about Buy: I would keep the service integration behind these tools. For example, `analyze_wallet` might use a paid blockchain data service to retrieve historical activity, but the external agent only needs to call OnFRA's `analyze_wallet`. It shouldn't have to understand which data provider OnFRA used.

The next thing I'd settle is the exact response contract for `analyze_wallet`, because that response will define what OnFRA means by wallet intelligence and become the foundation for several of the other tools.
